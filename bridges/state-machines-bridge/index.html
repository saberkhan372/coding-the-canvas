State Machines: Screens, Modes, and Transitions

A state variable names the current mode. draw() renders one mode at a time. Events change the state and move the sketch to a new screen.

One sketch can have many modes.

Students often build a game by piling every condition into draw(): if the mouse is clicked, if the score is high, if the timer is done, if the player is alive. A state machine makes the structure visible. The sketch is in exactly one mode now, and only some events are allowed to move it to another mode.

  • Use one variable to name the active mode: let state = "menu".
  • In draw(), choose exactly one screen based on that value.
  • Events create transitions: click, key press, score limit, timer end.
  • Draw the diagram first: states are circles, transitions are arrows.
  • Reset mode-specific variables when entering a new state.

Common misconception

"A state machine is a special advanced feature." — It is just a variable plus conditionals plus events. The power comes from naming the modes clearly and making transitions explicit, not from new syntax.

Before: scattered booleans

many flags can conflict 
let started = false;
let paused = false;
let lost = false;

function draw() {
  if (!started) drawMenu();
  if (started && !paused) drawGame();
  if (paused) drawPause();
  if (lost) drawGameOver();
}

This can accidentally describe impossible situations: started and lost, paused and not started, game over and still playing.

After: one state

one value names the mode 
let state = "menu";

function draw() {
  if (state === "menu") {
    drawMenu();
  } else if (state === "playing") {
    drawGame();
  } else if (state === "paused") {
    drawPause();
  } else if (state === "gameover") {
    drawGameOver();
  }
}

The sketch is in one mode at a time. That makes the code easier to read, test, and extend.

What students are really learning

A state machine gives structure to time. The sketch is not just responding to the current mouse position; it remembers where the user is in the experience. Menu, playing, paused, and game over are not separate programs. They are modes inside one program.

The diagram matters because it separates allowed moves from accidental ones. From "menu", a click can start the game. From "playing", a collision can move to "gameover". From "gameover", a click can restart. If there is no arrow, the code should not transition that way.

State

The current mode: "menu", "playing", "paused", or "gameover".

Render

draw() checks the mode and runs the screen logic for that mode only.

Transition

An event or condition changes the mode and may reset variables for the next screen.

Bridge moves

List the screens

Ask students to name every screen or mode before opening the editor. Keep the first version small: menu, playing, game over.

Draw arrows

For each arrow, write the event above it: click starts, collision loses, click restarts. This becomes the transition code.

Code one transition

Start with menu to playing. Then add one losing condition. Test each transition before adding another state.

Discussion question

Can the sketch be both "menu" and "playing" at the same time? What bug becomes possible if you use two booleans instead?

Follow-up: where should you reset score - while drawing the menu, or when transitioning into a new game?

AP connection

State machines combine variables, conditionals, events, and abstraction. They support AP CSP selection/iteration and AP CS A object design when each state delegates to methods.

p5.js - three-screen state machine 
let state = "menu";
let score = 0;

function setup() {
  createCanvas(400, 240);
  textAlign(CENTER, CENTER);
}

function draw() {
  if (state === "menu") {
    background(30);
    fill(255);
    text("Click to start", width / 2, height / 2);
  } else if (state === "playing") {
    background(246);
    score++;
    fill('#d96a3d');
    circle(width / 2, height / 2, 40);
    fill(30);
    text("Score: " + score, width / 2, 30);
    if (score > 180) {
      state = "gameover";
    }
  } else if (state === "gameover") {
    background('#fff8f5');
    fill(30);
    text("Game over - click to restart", width / 2, height / 2);
  }
}

function mousePressed() {
  if (state === "menu") {
    score = 0;
    state = "playing";
  } else if (state === "gameover") {
    state = "menu";
  }
}

3-minute demo script

Step 1. Ask students to name the screens in a simple game. Write menu, playing, and gameover as circles on the board.

Step 2. Add arrows and labels: click, lose, restart. Say: "These arrows are the only legal ways the sketch moves between screens."

Step 3. Code only menu and playing. Test the click transition. Then add gameover. Reset score when entering a new game.

Watch for: students resetting variables inside draw() every frame. Put reset logic in the transition, not in the screen's drawing code.
